## Method and data status

The [accepted design](2026-11-16-auto-routing-design.md) defines capability as a declared judgment on 0–3 with half-steps; unknown is not zero. [CRITERIA](../../lib/classifier-contract.mjs) distinguishes 0 micro (mechanical work), 1 low (well-specified low-risk coding), 2 medium (ordinary engineering with interacting constraints), and 3 high (hard, ambiguous or correctness-sensitive work). The two numerical entries are **low-confidence judgments**, not vendor-assigned tiers: narrow recommendations are mapped conservatively to a related criterion, without claiming general adequacy. All other entries are unknown, including where effort support or benchmark placement is known but does not establish tier adequacy. No half-step, monotonicity, cross-model offset, or provider ranking was inferred. The design's declared-below-demand precedence means a numeric estimate can displace an unknown; these two values need particular scrutiny.

The profiles list 24 distinct model/effort combinations: three Anthropic models × five efforts, and three custom models × three efforts. The table enumerates all configured supported efforts for each selected model, including efforts not reached by the current tables. None has an empty effort list; native-default handling therefore adds no row. Configured effort lists are not proof that each serving backend actually accepts an effort.

Scope: only execution models reachable from merged base/activity routes in any of the three table modes. Project/session mode overrides can select balanced or quality even when a profile selects cost. The mode enumeration used loadConfig, applyMode, and resolveRoute for every tier and activity including base; it is a static table reachability check, not observation of actual traffic, pins, runtime availability, or live project overrides. Activities inherit their tier route. The automatic engine's broader candidate set is not claimed to be limited to these routes.

## Profile mapping and exclusions

- router.json: inherited Anthropic defaults plus profile route overrides yield haiku, sonnet, opus (9 distinct mode-reachable pairs). Sonnet comes from inherited activity overrides; mode transformations change efforts.
- model-proxy-router.json: deepseek, glm-flash, kimi, sonnet, opus (14 mode-reachable pairs). haiku is configured but not reachable from these routes or transformations, so excluded.
- valar-router.json: deepseek, glm-flash, kimi (9 mode-reachable pairs). Model aliases shared across profiles are deduplicated in the table.

Subagent-only choices, classifier models, manually pinned or routing-off models, unused catalog models and possible runtime overrides outside those profile tables are excluded; auto routing v1 does not cover subagents. The [1m] suffix is removed only for catalog matching by the router's canonicalModel; it remains in exact configured IDs above. DeepSeek 1017 and GLM Flash match catalog aliases after this suffix removal. The Kimi namespaced ID does **not** exactly match a retained alias: [the similarly named K3.1 Pro record](https://github.com/alexei-led/model-cards/blob/91cc3b446da2187e7d115c3ae2f43e1ad3d92e37/moonshot/kimi-k3.1-pro/model.yaml) documents kimi-k3.1-pro, not moonshotai/Kimi-K3.1-Pro; it is cited only to expose the mismatch, not to infer identity or quality. No snapshot or near-name substitutes for this configured ID.

The model-cards catalog, selected manifests, overviews, prompting guides and cited local evidence were inspected read-only. Evidence is provider/deployment-specific and may be stale; a source's review date is not the date of a new provider check. Direct-API control documentation does not attest proxy behavior. No paid inference, provider probe, benchmark run, production trace, or claim of tested user-task quality is part of this proposal.
